# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

Until the first release, entries are grouped by **work area**, not by version.

## [Unreleased]

### Added

- **MV3 extension skeleton** — a WXT build with four entrypoints: background service worker, content script, popup and options. The permission set is fixed at `storage`, `activeTab`, `clipboardWrite` and `downloads` plus the `<all_urls>` host permission — never `tabs` and never `scripting`. `docs/ARCHITECTURE.md` §7.3 and a snapshot test pin it.
- **Tool DSL** (`packages/dsl`) — the §5.1 / §5.2 types, `matchUrl` with the §5.3 pattern semantics, a ReDoS-safe regex subset, and `validateToolDefinition` implementing all eight §5.4 rules. Every rejection carries a field-level `path`, a stable `code` and an English `message`.
- **Core contracts** (`packages/core`) — the message protocol (§7.2), the storage contract (§8.1) and the runtime contracts (§5.5). Types only, zero runtime dependencies.
- **Page analyzer** (`packages/analyzer`) — `analyzePage()` returns the §5.5 `PageAnalysis`: visible text simplified and cut to a character budget, repeating-unit container candidates with field-level candidates, a dynamic custom-element scan, and open shadow roots expanded. Read-only by construction: no DOM writes, no scrolling, no network, no model call.
- **Browser Adapter** (`packages/browser`) — the `BrowserAdapter` interface with a chrome implementation and an in-memory mock. Both run through one conformance suite, so "it passes in tests" keeps meaning something about the extension; the chrome implementation is stateless and looks the platform up per call, because an MV3 service worker is recycled without warning.
- **LLM package** (`packages/llm`) — the BYOK client (`callLlm`), the three-section prompt builder (`buildPrompt`: page content travels only in a wrapped data section — the §12.3 indirect-injection defence), nine `LlmError` categories the panels can tell apart, and the background side of `run:llm` / `run:llm_result` keyed by `requestId` with token usage attached. `api_key` is read in this package only: a source scan plus runtime assertions keep it out of the content script, the logs and every reply crossing back.
- **Storage** (`packages/storage`) — the three §8.1 keys behind a `BrowserAdapter`, with read-side defaults so a record written before `usage` existed still reads back complete, and an empty migration chain that already enforces version ordering.
- **Transform capability** (`packages/capabilities`) — filter / sort / regex / dedupe as local, deterministic ops with no permissions: a missing field never matches, mixed types sort by type instead of coercion, and every pattern passes the ReDoS safety subset before a single record is touched.
- **Render capability** (`packages/capabilities`) — mounts one of the three result views into Juxbly's own Shadow DOM mount point and nothing else. Zero records renders as a normal empty state, never an error.
- **Extract capability** (`packages/capabilities`) — `single` / `list` modes with `text` / `image` / `link` field types. Selectors pierce open shadow roots (closed ones are skipped, not probed); `image` reads `src` — falling back to the first `srcset` candidate — plus `alt`, and `link` reads `href` resolved to an absolute URL. An unparseable selector and a selector that matched nothing are deliberately different outcomes (`SELECTOR_SYNTAX` vs `hitCount: 0`), because health reads them on different layers. `pre_scroll` scrolls to the bottom first so lazy pages are not read one screen deep: capped at 10 rounds, stopped as soon as the page stops growing, and cancelled by the run's `AbortSignal`. Everything goes through `DomPort`, so the same code runs against a real page, a fixture and the candidate dry-run.
- **Result views** (`packages/ui`) — table / card / text views with the loading / empty / error split (`docs/UI_SPEC.md` §7). Values are rendered as text only, links require an `http(s)` URL, all colour comes from the §12 tokens, and long values and 500+ rows are capped.
- **Capability contracts** (`packages/core`, `packages/runtime`) — `CapabilityDefinition`, `ExecutionContext`, `RuntimePorts` and `CapabilityInput` (the step plus the records `input_from` resolves to), and a `CapabilityRegistry` that refuses duplicate step types.
- **Run engine** (`packages/runtime`) — `ToolRuntime` executes steps linearly, resolves `input_from` through a variable bag that rejects forward references and duplicate producers, and validates the definition before **every** run (a stored tool can be hand-edited in the open-source build). The llm cache decision is a stable 64-bit hash over a step's input data compared with `RunState.last_extract_hash`: unchanged data reuses the last output, and only an explicit `force` spends tokens again. A run returns `RunOutcome` — outputs, token usage, the render result, a `RunSummary` for health and the next `RunState` — and stores nothing itself; writing state stays with the caller. A cancelled run returns no state at all, so an abandoned run can never poison the cache.
- **LLM capability** (`packages/capabilities`) — the fourth registered capability. It owns no endpoint, no key and no prompt: it calls `RuntimePorts.llm`, which resolves to the background context, and returns the model's output together with what it cost. Its log line carries the task and the token counts, never the prompt or the output.
- **Shared logger** — every line carries a `[JUXBLY][<TAG>]` prefix, so it can be filtered out of a host page console. A content script shares its console with the page it runs on, so unprefixed logging would be hostile to whoever is debugging that page.
- **`docs/contributing/SCOPE.md`** — what V1 deliberately does not do, and why.
- **Web corpus** (`tests/benchmark/corpus/`) — 50 real-site snapshots across the five bucket classes (A 12 / B 10 / C 10 / D 8 / E 10). Each carries its `SnapshotMeta`, the measurement that put it in that bucket, and the robots.txt result actually fetched for it. There is one write path, `scripts/snapshot-site.mjs capture-sources`, and it refuses a site on any of four gates — robots, bucket verification, secret scanning, size. Health check: `pnpm test:corpus`.
- **Task corpus and ground truth** (`tests/benchmark/cases/`, `tests/benchmark/ground-truth/`) — one task per snapshot, written the way a user would ask it; the checker rejects task descriptions that leak selectors, DOM APIs or CSS fragments. Each task has a ground truth with an `item_count_range` narrow enough to be falsifiable, a representative `sample`, and provenance (`labelled_by` / `source` / `amendments`). The correct / partial / wrong judgement criteria live in `docs/benchmark/README.md`.
- **Benchmark runner** (`apps/playground/src/bench/`, `pnpm test:bench`) — runs the real pipeline over the corpus (snapshot → page analysis → propose → execute) and writes an immutable `results/<run-id>.json` plus a report carrying the corpus revision, model, date, failure excerpts and a delta against the previous run. Metrics are Build Success Rate, correct / partial / wrong, Clarification Rate (proxy), health false-positive rate, latency and tokens, every one of them split by bucket. The runner never judges a result itself: labels come from `results/labels.json`, and unlabelled cases count as `pending`. Without an API key it prints SKIPPED and exits 0. CI runs a 5-case slice on pull requests that touch the shared core; the full run is `workflow_dispatch`.
- **`":self"` field selector, and `FIELD_SELECTOR_EMPTY`** (`packages/dsl`, `packages/capabilities`) — `extract` reads every field with a selector relative to the container, and a container is never among its own `querySelectorAll` matches, so "the value is this element" was inexpressible; the benchmark showed the model writing `""` or `:self` for it anyway and failing the whole step after the rows had been found. A field selector may now be `":self"` (`docs/ARCHITECTURE.md` §5.2), and an empty one is rejected at validation as `FIELD_SELECTOR_EMPTY` (§5.4 rule 10) instead of throwing `SELECTOR_SYNTAX` mid-run. `":self"` was chosen over `self` — a valid type selector that would silently match nothing — and over `:scope`, real CSS whose `querySelectorAll` result legitimately excludes the scope element. It adds vocabulary, not control flow.
- **`MODEL_UNAVAILABLE` is its own `LlmErrorCode`** — a 403 is not a bad key. The endpoint accepted the key and refused the model (region or account), and filing it under `AUTH` sent the user to re-check the one thing that was already right. The connectivity test reports it as a fourth category with a next step that can work: try a different model.
- **Field-level scoring** (`apps/playground/src/bench/scoring.ts`) — the benchmark now measures what came out, not only that a tool was built. Build success cannot tell "built" from "built the wrong thing": on the 56-case corpus 92% of tools build while the asked-for fields arrive at F1 43.1%. Scoring is mechanical — no model, no judgement, no thresholds — so it can run on every push. Fields are matched **by content, not by name** (a column called `stock` where the ground truth says `availability` is not wrong); truncation counts as a match only when there is enough of one (the shorter side must be at least six characters and at least half the longer one, so `"£"` does not count as `"£63.00"`); and columns nobody asked for count against precision. Reported as recall, precision and F1, corpus-wide and per bucket, beside item-count-in-range.
- **Record and replay** (`apps/playground/src/bench/digest.ts`, `node scripts/bench.mjs --replay <digest>`) — a published number nobody can reproduce is an opinion. Raw result files stay gitignored (half a megabyte a run, impossible to regenerate); what gets committed is a **digest**: the tool the model proposed plus the facts measured around it. Everything after the proposal is deterministic, so the same tool against the same frozen snapshot reproduces the same items. Replay needs no key and calls no model — so it runs in CI on every pull request (`benchmark.yml`), and any difference against the recorded number is **drift**, which fails the job rather than being adopted as if nothing had happened.
- **`scripts/bench-breakdown.mjs`** — cuts a reading by fields asked for, by bucket, and by the two crossed, replaying committed digests. The headline F1 is one number over 56 cases and one number cannot say *where* the loss is; twice the answer to "where" was computed by hand in a scratch file that was then deleted, leaving a published number nobody could check.
- **Six single-field cases** (`A-13`, `A-14`, `C-11`, `D-09`, `E-11`, `E-12`) — the corpus moves from 50 to 56 (A 14 / B 10 / C 11 / D 9 / E 12). Seven single-field cases was too thin to support any field-count claim, and `A` had none. They are unlabelled by design: their readings come from field-level F1, which needs no human label.
- **A wider, cross-item field-candidate menu** (`packages/analyzer`) — `collectFields` now samples five items per container instead of reading one, and offers a field only if it is present in at least 40% of them (`MIN_FIELD_PRESENCE`), so a promoted slot, a "sponsored" badge or a header row that is really a header is no longer offered as a field of every item; `MAX_FIELD_HINTS` rises 8 → 12. A candidate whose value already appears under another accepted selector is dropped, and the deeper of the two wins.
- **Candidate selection as its own module** (`apps/playground/src/bench/selection.ts`) — `first-valid` (the first candidate that passes §5.4) and `best-scored` (every candidate dry-run against the snapshot, highest score wins — the product's own §5.6 "the model proposes, the page decides", applied at benchmark scale). Shared by the live run and the replay, because two paths that pick differently would make a replay measure a different experiment than the run it claims to reproduce.
- **A closed-loop repair round** (`apps/playground/src/bench/repair.ts`) — after the selected tool's first execution, the first rows it actually pulled go back to the model, which returns corrected candidates. The adoption rule is ground-truth-free on purpose: ground truth must never enter the loop or the run is measured against the answer.
- **Manifest icons and browser action** (`apps/extension/manifest.ts`) — the manifest declared neither, so Chrome showed the default puzzle piece in the toolbar. Sizes are committed in `apps/extension/public/` from the 2048px master.
- **Mechanical pre-labelling** (`scripts/prelabel.mjs`, `tests/benchmark/results/labels.json`) — the judged half of the benchmark needs 50 judgements per round, which no one can afford per iteration. The script proposes a label per case by comparing the run against each ground truth's `item_count_range` and `sample`, and writes a review table carrying the failing kind, a confidence and the evidence. It proposes; it does not judge. A case whose infrastructure failed stays `pending`, `structure-changed` is never assigned offline, and a label becomes real only when a person accepts it.

- **An `attr` field type, so a value that lives outside the text node can be read** (`packages/dsl`, `packages/capabilities`, `packages/llm`) — `FieldType` gains `'attr'`, paired with a new `field_attrs` map that names the attribute to read (`"field_types": {"rating":"attr"}, "field_attrs": {"rating":"class"}`). It came out of the first dogfooding pass: books.toscrape encodes its star rating as `<p class="star-rating Three">` and keeps the untruncated book title in `title=`, so `text` returned an empty `rating` column on all 20 rows and a clipped `title`. Those two instances were the only unreachable ones in the whole corpus — 2 of 114 field instances, the other 107 already reachable by `text` / `link` / `image`. `field_attrs` is a sibling map rather than selector syntax (`p.star-rating@class`) because the selector string goes to `dom.query` unchanged, and a second dialect inside it would have to be parsed by every consumer including `:self` handling and the highlight layer. Validation rejects `attr` without a name (`FIELD_ATTR_REQUIRED`), an empty name (`FIELD_ATTR_EMPTY`), a name that is not a field (`FIELD_ATTR_UNKNOWN_FIELD`), and an unknown type (`FIELD_TYPE_UNKNOWN`). **An attribute whose name marks a credential slot is refused at read time** — the same narrowed rule corpus capture already enforces — because `attr` is also the first thing in the product that can bulk-copy a page's hidden values into a table a user then exports as CSV or JSON; a refused read reports as an ordinary missing field, and never fails the run. The build prompt teaches the type and tells the model when to reach for it; in the dogfooding re-run the model chose it without hand editing. Evidence, including the before/after rows: `tests/benchmark/reports/dogfood-2026-10-30.md`.
- **Two published recipes** (`docs/recipes/quotes-toscrape-quotes/`, `docs/recipes/books-toscrape-books/`) — the first preset seeds from stage 3-1, built by the extension itself on real pages and verified by reading the rendered table. Both pages are already corpus cases (`A-02`, `A-01`), so a recipe and the corpus measure the same thing. `books-toscrape-books` is the worked example for `attr`.
- **A dogfooding harness** (`scripts/dogfood.mjs`, `pnpm dogfood`) — one request against one **live** page, typed and clicked the way a person would type it, in real Chromium against a live model, reusing the lifecycle harness's browser and step helpers so the acceptance path and the dogfooding path exercise the same surface. The benchmark replays frozen snapshots against recorded answers, so it can only ever find again what it has already seen; this is what surfaced the missing `attr` field type, and the script that produced those two readings lived in `/tmp` — unquotable, unrepeatable, and gone with the machine. Each pass writes screenshots of the proposal and the result, the saved tool record, and a `report.json` carrying the row count, a row sample, wall-clock timings, the token counts the UI displayed, and every page error. Cost and latency are recorded because the first dogfooding pass had neither: without them two runs of the same request cannot be compared, and these steps spend money that belongs to whoever owns the key. Output lands in `.dogfood/` (gitignored) because it is live page content; a recipe is still authored from a pass afterwards, by hand. `docs/DEVELOPMENT.md` §Dogfooding.
- **Two more preset seeds from dogfooding** (`docs/recipes/webscraperio-first-table/`, `docs/recipes/scrapethissite-countries/`) — built by the extension on the live pages of corpus cases `A-03` and `A-13`, confirming their proposals through the real UI, each verified by reading the rendered table out of a real browser. `A-03` agreed with its ground truth field for field; `A-13` returned 250 complete rows while being asked for one column, and ships untrimmed for that reason — curating a tool after the fact and still calling it *verified* would publish a definition nobody has ever run. Three further attempts on `A-03` could not even reach the floating ball, because the site's cookie-consent banner covers it; that is recorded rather than worked around, since a dogfooding harness silently clicking through someone's cookie choice is not a thing to build quietly. Evidence, costs and latency: `tests/benchmark/reports/dogfood-2026-10-30-second-pass.md`.
- **A guard test for published recipes** (`tests/unit/recipes.test.ts`) — every `docs/recipes/*/recipe.json` is validated as data: the definition must pass `validateToolDefinition`, `scenario.capabilities` must match the step types actually used, the health baseline must carry a **range** and no scraped content, its expected fields must match what the extract step really produces, and `scenario.url_pattern` must equal `definition.url_pattern`. Written because all of those were violated by hand-written versions at least once, and "I'll check the diff" is exactly the promise that leaks a credential.
- **A per-field transform, so a value that arrives wrapped can end up as the value that was asked for** (`packages/dsl`, `packages/capabilities`, `packages/llm`) — `extract` gains an optional `field_transforms` map (field → ordered op list) with exactly one op in V1: `capture`, which keeps the regex match (or a numbered group) from the value that was read. It closes the class `attr` opened: books.toscrape's rating became reachable as `class="star-rating Three"` the day `attr` landed, but what the user asked for was `Three` — and the attr entry below records, in the scorer's own words, that this needed a per-field transform the DSL still lacked. The transform shapes the value **after** the read, so the selector string stays untouched — `dom.query`, `:self` handling and the highlight layer learn nothing new. The op list is whitelist-vocabulary rather than control flow, and §5.4 rule 11 refuses at save time, with named codes, an unknown op, an empty list, a missing or unsafe pattern (the same safe-regex subset rule 6 pins for the `regex` transform op), a negative group, a key that is not a field, and a transform on an `image` field — whose value is `{src, alt}`, not a string. The capability re-checks the patterns per step (`assertTransformPatternsSafe`) for a caller that bypassed validation. A failed capture reads `''` — the value `fieldPresence` already counts as missing — never an error mid-run. The build prompt teaches the op with the books example and the "In stock (19 available)" one. Evidence, including the before/after rows: `tests/benchmark/reports/dogfood-2026-10-31.md`.
- **A save whose URL pattern points elsewhere says so** (`packages/llm`, `packages/ui`, `apps/extension`) — dogfooding caught a silent dead end: the build prompt constrained `url_pattern`'s *syntax* but never required it to match the page being built, so a model output like a detail-page path on a list page saved fine, matched no tool on the current page — and the post-save run mount sat hidden in the initial `loading` phase forever, because a zero-tool session had no terminal state and the panel only reveals itself when tools exist. Now the prompt requires the pattern to match the page URL in the data section; `start()` with no matching tools settles on the empty phase; and the mount a save causes reveals the panel at once, landing on a dedicated no-tool guidance line (`run.no_tool`) instead of an unanswered click. `docs/UI_SPEC.md` §7.6. Evidence and diagnosis: `tests/benchmark/reports/dogfood-2026-10-31.md`.
- **The dogfooding output directory is outside the linter's tree** (`eslint.config.js`) — `.dogfood/` holds regenerable, never-committed run artefacts whose scratch scripts are not product code; linting them made `chrome.*` restrictions fire on a diagnostic driver that only the extension's own context may satisfy. The same reason `tests/benchmark/results/*` stays out of the tree.
- **Build-proposal compliance, hardened against a drifted model snapshot** (`packages/llm`) — the 2026-10-31 live gate reading found build success collapsed 92.0% → 69.6% with a 0.0pp spread: 9 of 14 generation failures wrote a `category` outside the enum the schema line already listed, and 3 died to empty completions that parse to a non-object. The prompt now states the category rule in words — exactly one of the four values, never a synonym — and an empty reply is retried once, only when the reply parsed to no object; a parsed answer with zero candidates is the model deciding, and is not retried. Post-fix reading: field F1 47.8% / 47.1%, **median 47.4% ≥ 47% — the second gate reads met** on the same corpus, the same scorer, no ruler change (spread 0.7pp; both runs individually above the line). Build success recovers to 76.8% but not to 92.0% — the drifted snapshot is worse at compliance, and the residue is a measured robustness track, not a ruler question. Full numbers, route note and failure attribution: `tests/benchmark/reports/attribution-2026-10-31-f1-ceiling.md` §8.
- **The Policy Surface lands: a Store Build that asks for each origin when it is needed** (stage 3-2, `apps/extension`, `packages/browser`, `packages/ui`) — one codebase, two manifest variants, resolved from `apps/extension/manifest.ts` and locked by test. The Open Source Build is unchanged (`<all_urls>` static); the Store Build (`JUXBLY_VARIANT=store`, `pnpm build:store`) narrows static host permissions to the default provider origin (`https://api.openai.com/*`, paired with `DEFAULT_API_BASE_URL` and locked to it) and declares the rest as `optional_host_permissions`. The content script keeps `matches: ['<all_urls>']` — Chrome injects it only where the origin is granted, so both builds share one code path and no `scripting` permission ever appears. Grants are requested through a fifth adapter port (`permissions`), the only caller of `chrome.permissions.*`, from three surfaces, each inside the user's own gesture: the popup's "Enable on this page" (renders only when the active origin is ungranted, so the open-source build never shows it — permission state is the branch, no runtime variant flag), the options page when saving or testing a BYOK endpoint (a declined grant is reported as "no access to this endpoint", never misread as a network failure, and never blocks the save), and preset installation (Track B, below). The popup asks "which page is open" via a new read-only `tab:active_url` message answered by the background's already-sanctioned `tabs.query` — still no `tabs` permission, in either build. Two store-build degradations are accepted and documented rather than papered over: an ungranted tab's URL reads as absent, so overview clicks focus-or-open without misjudging; the screenshot fallback fires only where the origin is granted or `activeTab` covers the tab. Rationale: `docs/concepts/policy-surface.md`; contract: `docs/ARCHITECTURE.md` §7.3.

### Changed

- **`ValidationResult` is a discriminated union** (`{ ok: true; value } | { ok: false; errors }`). The previous shape could not carry `value` on success, which forced callers into casts or undefined checks at the only gate between model output and execution.
- **The content script mounts an empty, hidden `#juxbly-root`** with an open shadow root. This is the host the UI will render into; nothing is visible yet.
- **The run engine refuses every `export` step, not only `copy`** (`packages/runtime`) — `csv` and `json` hand a file to the download manager with nothing on screen that says so, which turns a visible wrong table into a silent wrong artefact on disk. A run is unattended by definition, so all three formats are refused before `input_from` is resolved; the panel's resident Copy / CSV / JSON buttons remain the only delivery path and call the ports directly from the click (Maintainer ruling 2026-09-22). The step stays in the type so a hand-written tool fails with a named reason instead of being rejected as unknown syntax.
- **The median is the average of the two middle values** (`medianOf`, `apps/playground/src/bench/metrics.ts`). The phase gates are written as "the median of two runs", and the previous `values[length / 2]` shortcut returns the **upper** of two readings — the better one, in the one direction `docs/benchmark/README.md` forbids. Of 37.4% and 38.7% the reading is 38.1%, not 38.7%.
- **Repair success rate is measured when a run attempted repair** — previously always `null`. A case with `not-attempted` is not a denominator, and `null` still means "no attempt", never `0%`.

### Decisions worth knowing

- **Tool Health ships all four layers in V1** — execution, result, structure fingerprint and semantic. The earlier "structure fingerprint interface only, semantic later" position is superseded. Semantic is the only token-consuming layer: it fires on deviation only, is throttled, and its token cost is always shown.
- **Copy is English first** (the product targets EU/US markets). V1 ships `en` only, but the i18n structure — keyed copy in `packages/ui/src/copy/` — is in place from V1, so adding a language is a locale change rather than a refactor.
- **Result-first delivery**: the narrative is *describe a need → get the result → it is still there next time*. The result ships in front, the tool is attributed on the result itself, and keeping it is the default.
- **The benchmark reports what it measured, not what flatters it**: an environment failure (network, endpoint unreachable) is recorded as an error and excluded from the rate, never counted as a 0% result; and a metric the runner cannot observe — repair success rate, since the runner never repairs — is printed as *not measured* instead of 0%.
- **Silent auto-repair is out.** A failing tool is never rewritten in the background: repair produces a new, user-confirmed version and the old one stays available.
- **No confidence score.** It was trialled before implementation and did not predict correctness, so it is not in V1.
- **Build success is not correctness.** The benchmark's first judged run produced a tool for 90% of cases and a *correct* tool for 10%. Fixing a failure moves it to the next layer down rather than removing it — every round so far has traded build failures for field-semantics failures — so a benchmark report carries both numbers and failure composition, and a claim that the product improved is made about correctness, never about build success alone. Measurements and the rules for iterating are in `docs/architecture/selector-quality.md`.
- **A per-site selector knowledge library is deferred pending validation** — not rejected. None of the three measurements that would justify it exist yet: the same site failing the same way across two or more rounds, failure mass concentrated in a few sites rather than spread evenly, and a health signal that detects a break before a user reports it. The conditions are written into `docs/architecture/selector-quality.md` so the next pass is a measurement rather than an argument.
- **Phase 3 is entered on two staged gates, not one** (Maintainer ruling 2026-09-20). Build Success Rate ≥ 85% gates **3-1 dogfooding** and is met (92.0%, the median of two runs of one configuration on the 56-case corpus); field-level F1 ≥ 47% — the 43.1% baseline plus one 4pp noise band — gates **3-3 store release** and is not met. A tool that builds but returns the wrong fields is good enough to learn from and not good enough to promise to strangers, and dogfooding is the only source of the real-usage signal Phase 4 is conditioned on, so holding it behind a lab metric read on 56 cases would trade a decision made on evidence for a decision made on a proxy.
- **A reading is two runs of one configuration, and the spread is part of it** (`docs/benchmark/README.md`, "Taking a reading"). Report the median, never the better of the two; a difference under 4pp is noise, not an improvement; a spread wider than 8pp is not a reading at all. Every published number names the digest it was replayed from, and a threshold is re-measured whenever the corpus revision changes — a threshold measured against a corpus that has since been re-captured is a threshold against a different ruler. That already happened once: six single-field cases moved the baseline 38.0% → 43.1% on an engine that had not changed, and it is recorded as a new ruler, not as progress.
- **The launch promises two page shapes, not five** (Maintainer ruling 2026-09-22). By bucket the readings put `A` (semantic structure) at 64.7% and `D` (lazy-loaded lists) at 55.9%, `C` (shadow DOM) at 41.6% but spread 9.4pp across two runs — too wide to be a reading — and `B` (SPA) at 21.3% and `E` (hashed classes) at 18.4%. Store copy, UI and the launch preset pack promise `A` and `D` only. This narrows the promise, not the product: engine-side improvements to `B`/`C`/`E` still land, and widening the promise re-measures the gate under the same rule.
- **The cheap engine-side experiment series is closed.** Field-level F1 has not moved outside the noise band under any change tried: five prompt-side runs of the previous corpus (35.9% – 38.8%), both engine-side variants of 2026-09-19 (negative), a widened field-candidate menu (2026-09-22: +2.7pp, inside the 4pp band — though the share of fields taken from the offered menu rose 57.5% → 78.0%), and a closed-loop repair round that proved inert (in a paired per-case analysis the correction changed extraction behaviour in only 1 of 82 paired cases). Reaching 47% now requires an architecture-level change — for example a restricted operator pipeline in the DSL — which is a Maintainer decision, not another prompt or selection rule.

- **A populated column is not necessarily an improved metric** (measured 2026-10-30). The `attr` change is larger than it sounds as a caution about reading benchmark numbers. It fixed a real defect — `rating` went from empty on all 20 rows to populated — and the field-level F1 did not move at all, for two reasons that only showed up when the pairs were run through `matches`: the previously **truncated** title already scored as a match (it was a long enough prefix of the expected value), and the **new** `star-rating Three` still does not (`Three` is 5 characters, under the scorer's 6-character floor, so it needs an exact match it cannot get from a prefixed attribute). So the same change is a genuine user-facing improvement and a zero to the gate. Both are reported; neither is rounded to the flattering side. The consequence for the roadmap is unchanged: the cheap engine-side series stays closed, and this architecture-level change did not reopen it. It also leaves one thing genuinely open — getting `Three` rather than `star-rating Three` needs a per-field transform, which the DSL still lacks.

## Release notes format

Each release records:

- **Added**
- **Changed**
- **Fixed**
- **Breaking Changes** (if any)
- **Security Notes** (if any)

## Version and release policy

- Releases use explicit semantic versions.
- `main` is protected; changes reach it through review.
- A release is cut after the relevant acceptance criteria are verified.

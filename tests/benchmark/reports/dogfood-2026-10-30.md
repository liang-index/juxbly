# Dogfooding record — 2026-10-30

The 3-1 gate (Build Success Rate ≥ 85%) was met on 2026-09-20. This is what the first
dogfooding pass found once the extension was pointed at **live sites with a live model**,
driven through the real UI in a real browser.

Nothing here is a lab number. Every row below was produced by the built extension running
in Chromium against a page on the public internet.

## How it ran

| | |
|---|---|
| Build | `.output/chrome-mv3`, manifest v3, v0.1.0 |
| Model | `deepseek-chat` over the BYOK channel, live key, not a recording |
| Driving | clicks and typing only — the same step helpers `pnpm test:e2e` uses |
| Compared against | corpus cases `A-01` and `A-02`, whose snapshots are the same two pages |

This is deliberately a *live* run. The corpus replays recorded answers; dogfooding exists to
find what the recordings do not contain.

## Reading 1 — `quotes.toscrape.com` (corpus case `A-02`) — clean

Request: *"Collect every quote on this page: the quote text, the author, and the tags."*

The build asked one clarifying question, was answered once, proposed three fields, and was
confirmed. Result:

| Check | Result |
|---|---|
| Rows | 10 — matches `A-02`'s range exactly |
| `text` | correct, full quote including typographic quotes |
| `author` | correct (`Albert Einstein`, `J.K. Rowling`, …) |
| `tags` | correct per-row values |

Three of three fields right, ten of ten items. This became
[`docs/recipes/quotes-toscrape-quotes/`](../../../docs/recipes/quotes-toscrape-quotes/README.md).

## Reading 2 — `books.toscrape.com` (corpus case `A-01`) — one field unreachable

Request: *"Collect every book on this page: the title, the price, whether it is in stock, and
its star rating."*

Result: 20 rows (matches `A-01`'s range exactly), but:

| Field | Result | Why |
|---|---|---|
| `price` | correct | `p.price_color` text |
| `stock` | correct | `p.instock` text |
| `title` | **truncated** | the page truncates the anchor's visible text; the full value sits in the `title` attribute |
| `rating` | **empty on all 20 rows** | the page encodes it as a CSS class — `<p class="star-rating Three">` — there is no text node |

`readFieldValue` offers exactly three field types: `text` reads `textContent`, `link` reads
`href`, `image` reads `src`/`srcset`. **There is no way to read an arbitrary attribute**, so a
value carried in `class` or `title` cannot be extracted today. The proposal read
`p.star-rating` as `text` and got the empty string, twenty times.

Reproduced twice, same result both times.

## Reading 3 — the same page again, after `attr` was added

Field types are now `'text' | 'image' | 'link' | 'attr'`, with a `field_attrs` map naming the
attribute `attr` reads (Maintainer decision 2026-10-30; see the code note below). Same page,
same request, real model, real browser:

| Field | Before | After |
|---|---|---|
| Rows | 20 | 20 |
| `price` | `£51.77` | `£51.77` |
| `stock` | `In stock` | `In stock` |
| `title` | `A Light in the ...` | `A Light in the Attic` |
| `rating` | `""` on all 20 rows | `star-rating Three` |

The model picked the new shape on its own — no hand editing:

```json
"field_types": {"price":"text","rating":"attr","stock":"text","title":"attr"},
"field_attrs": {"rating":"class","title":"title"}
```

The empty column is gone. This is a real improvement to what a user sees.

### It does not move field-level F1. Measured, not estimated.

`matches` in `apps/playground/src/bench/scoring` is a prefix rule with a floor: the shorter
side must be at least 6 characters and at least half the longer one. Run against the actual
pairs:

| Field instance | Before | After |
|---|---|---|
| `rating` (`""` → `star-rating Three` vs `Three`) | miss | **miss** |
| `title` (`A Light in the ...` → full vs `A Light in the Attic`) | **match** | match |

Two things follow, and both cut against the obvious reading of the table above:

- The `title` fix is invisible to the score — `A Light in the ...` already matched, because
  the truncated form is a long enough prefix of the expected value.
- The `rating` fix is likewise invisible — `star-rating Three` carries the `star-rating`
  prefix, and `Three` is only 5 characters, under the 6-character floor, so it cannot match
  unless it is exact.

So the honest number for this change, measured: **zero change to field-level F1.** It makes
the product better and the benchmark score identical, which is not the same thing as failure
— it is also not evidence that the second gate got closer. Anyone quoting this change as
progress toward 47% would be quoting it wrong.

Reading it the other way: the corpus-scale measurement above said the attribute gap covered
1.8% of field instances. This says even that 1.8% was never actually costing recall, because
the scorer was already crediting the degraded forms. The cheap-engine-experiment conclusion
survives intact, and this architecture-level change did not overturn it.

### One thing worth deciding separately

`rating` comes back as `star-rating Three`, not `Three` — `attr` returns the whole attribute,
so class-encoded values arrive with their prefix. Trimming it needs either a post-extract
operator or a per-field transform, both of which are DSL changes beyond this one. Not done
here; recorded instead.

## How much of the corpus this actually covers

Measured mechanically, before the change landed: every expected field of every case was
checked against its snapshot to see whether its ground-truth values are reachable by the
three field types, reachable only via some other attribute, or invisible to a DOM-only parse.

| Verdict | Instances | Share |
|---|---|---|
| Reachable today (`text` / `link` / `image`) | 107 / 114 | 93.9% |
| Reachable only via an unreadable attribute | **2 / 114** | **1.8%** |
| Not visible to the probe (shadow DOM, lazy content) | 5 / 114 | 4.4% |

Both attribute-gap instances are the two above, on `A-01` — the same page the live run failed
on. Per bucket: `A` 94.3%, `B` 100%, `C` 75%, `D` 100%, `E` 100% reachable (`C`'s five
misses are all the probe's blind spot, not product misses — a DOM-only parse cannot see into
shadow roots, and those cases need a real browser to measure).

**The honest conclusion: this is not the lever on the field-F1 gate.** 1.8% of field instances
cannot move a 43.1% baseline to 47%, and Reading 3 above measured the actual effect of closing
the gap at **zero**. It is still a real defect worth fixing on its own merits — a 20-row table
with a silently empty column is a bad product moment — but it must not be reported as progress
toward the second gate, because it is not.

The cheap engine-side experiment series remains closed (Stage 3 entry conditions). Adding an
attribute-reading field type would be an architecture-level change to the DSL, which is a
Maintainer decision, not the next experiment.

## Two other things the live runs showed

- **Output shape is not stable across runs.** The same books request produced a 4-column table
  on the first run and a 5-column table (an extra `link`) on the second. Field-level scoring
  tolerates column renaming, but a column that appears and disappears changes precision.
- **Cost was not captured.** The dogfood harness did not record tokens or latency for these
  runs, both of which the metrics table asks for on any run that used a step that calls the
  model. These two runs did not — no `llm` step — so nothing is missing here, but any future
  dogfooding pass that does should record them.

## Reproducing

```bash
pnpm build
JX_OUT=<prefix> node <dogfood script> <url> <task> [answer to the clarifying question]
```

The script is not in the repository yet — this pass was run from `/tmp` to avoid committing a
tool before its output was worth keeping. It is worth keeping now; landing it is a separate,
small change.

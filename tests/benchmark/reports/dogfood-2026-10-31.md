# Dogfooding record — 2026-10-31

This pass closes the question the [2026-10-30 record](dogfood-2026-10-30.md) left open:
`attr` made `class="star-rating Three"` readable, but the column still read `star-rating Three`
when what was asked for was `Three`. That record ended with "needs a per-field transform …
recorded instead". This is the after.

Nothing here is a lab number. Every row below was produced by the built extension running
in Chromium against a page on the public internet, through the real UI.

| | |
|---|---|

## Reading 1 — the transform, end to end

Request: *"Collect every book on this page: title, price, rating, and whether it is in stock."*

| Field | 10-30 (`attr` only) | This pass (`attr` + `capture`) |
|---|---|---|
| Rows | 20 | 20 |
| `price` | `£51.77` | `£51.77` |
| `stock` | `In stock` | `In stock` |
| `title` | `A Light in the Attic` | `A Light in the Attic` |
| `rating` | `star-rating Three` | **`Three`** |

The model added the transform on its own — no hand editing:

```json
"field_types": {"price":"text","rating":"attr","stock":"text","title":"attr"},
"field_attrs": {"rating":"class","title":"title"},
"field_transforms": {"rating": [{"op": "capture", "pattern": "\\w+$"}]}
```

Cost and latency, read off the UI the harness records: proposal 2 059 ms, 2 571 build tokens,
run settle 3 450 ms, no `llm` step (the run panel showed no per-run token line — the honest
absence, not a zero). Three further passes the same morning (two diagnostic, one harness)
also proposed transforms unprompted — on `rating` (`\w+$`), on `stock` (`\d+`), on a 4-field
proposal — so the model reaching for the op is not a one-off.

On the gate: this still does not move field-level F1 on its own. The scorer's prefix rule
credits `star-rating Three` against `Three` no better than `""` did (the 6-character floor),
so the corpus-scale number for this change is **zero by construction** — the same honesty the
`attr` entry was held to. It closes a real product gap: a user asking for a rating should not
receive a CSS class.

## Reading 2 — a save that says nothing (found, then fixed)

Two harness passes on the same page and task hung after clicking **Looks right**: the build
panel closed and no run panel ever appeared. The run panel was in the DOM, hidden,
`data-phase="loading"`, for the full 90 s budget.

What the diagnosis (a throwaway driver that polls the build panel's phase, storage and the
`run:query_tools` reply) established:

- The proposal had displayed, so it had passed validation — and `confirm`, the background save
  and the panel all run the **same** `validateToolDefinition`, so the save could not have been
  the differing gate.
- Replay passes with the same task and build succeeded end to end, transforms included — the
  failure was not the new `field_transforms` code path.
- The one mechanism consistent with every observation: the model proposed a `url_pattern` that
  does not match the page it was built on. The save then succeeds, the post-save run mount
  queries matching tools, gets an empty list — and sat in the initial `loading` phase forever,
  hidden. (The temp profiles of the two failing passes are gone, so the pattern itself could
  not be read back; the wording here claims only what was observed.)

Two product facts made that silence possible, and both were fixed in the same change:

1. **The prompt never said the pattern must match the page.** The model sees the page URL in
   the data section; the rules constrained the pattern's *syntax* only. The rule now says the
   pattern must match the page URL in the data section, so the tool runs where it was built.
2. **A zero-tool run session had no terminal state.** `start()` with no matching tools left
   `phase: 'loading'` forever, and the panel is hidden unless tools exist — so a save whose
   pattern pointed elsewhere left the user staring at nothing after clicking "Looks right".
   Now: zero tools settles on the empty phase with its own guidance line (`run.no_tool`), and
   the mount a save causes reveals the panel immediately — "Running…" is honest there because
   the user acted a second ago. `docs/UI_SPEC.md` §7.6 documents the state.
